# Спецификация: Auth, роли и доступ

Продукт: школьный портал «Средняя школа». Документ фиксирует контракт авторизации, чтобы агент и человек говорили на одном языке о доступе.

## Намерение

- Публичные страницы открыты всем.
- `/admin` и `/kk/admin` доступны только авторизованным пользователям с ролью `super_admin`, `moderator` или `editor`.
- Роли хранятся в таблице `profiles.role` и проверяются на клиенте через RLS + middleware, не на доверии к URL.

## Роли и права

| Роль | Доступ в админке |
| --- | --- |
| `super_admin` | Всё: пользователи, роли, контент, учителя, расписание, обратная связь |
| `moderator` | Контент, учителя, расписание, кабинет доверия |
| `editor` | Только новости и объявления |
| `student` / `teacher` / `parent` | Без админки (публичный сайт, личный кабинет) |

Источник прав: `src/lib/auth.ts` (`ROLES`, `ADMIN_ROUTES`). Фактический файл имеет приоритет над этой таблицей при расхождении — обновите оба.

## Механизм проверки

1. Вход: Supabase Auth, OTP по email (шаблон `magic_link`, код = `{{ .Token }}`).
2. Сессия хранится в cookies `sb-access-token` / `sb-refresh-token`.
3. `src/middleware.ts`: для `/admin` и `/kk/admin` восстанавливает сессию через `setSession`, читает `profiles`, при отсутствии прав редиректит на `/login` или `/`.
4. API-эндпоинты в `src/pages/api/**` дополнительно проверяют роль перед операцией.
5. RLS в `supabase-schema.sql` — нижний уровень защиты: прямые запросы от клиента ограничены политиками по `auth.uid()`.

## Acceptance criteria

- Неавторизованный → `/admin` редиректится на `/login`.
- `editor` → `/admin/users` получает отказ (404/редирект), новости доступны.
- `moderator` → управляет учителями/расписанием/обратной связью, но не пользователями.
- `super_admin` → все разделы доступны.
- Ни один клиентский запрос не использует service_role ключ.
- Все правила RLS покрывают: выборку, вставку, обновление, удаление для каждой таблицы.
